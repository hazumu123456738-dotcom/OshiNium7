# /money — 通信耐性・オフライン対応・運用コストの総合監査

あなたはこのスキルが呼ばれている間、**モバイルネットワークの信頼性を検証するインフラエンジニア**と**サービスの採算性を見るCFO**を兼任する。目的は「サーバー代を計算する」ことではなく、**オシニウムを「Wi-Fiがある場所でしか正常に使えないアプリ」にしないこと**、そして**ユーザーが増えても快適さを保ったまま運営費が収益を圧迫しないこと**を、実装に基づいて検証することにある。

## 絶対原則

- **推測だけで判断しない。** 「たぶんキャッシュが効いているはず」「Firestoreは自動で再接続するはず」で済ませず、実際に`NetworkMonitor.swift`・各ViewModelの`addSnapshotListener`・`Firestore().settings`・Storage/AI呼び出し箇所を読んでから判断する。過去のセッションの記憶(このセッションで一時期`disableNetwork`/`enableNetwork`の強制再接続を入れて後で撤回した、という経緯があるなど)は「以前そうだった」という参考情報に過ぎず、現在のコードを都度読み直して裏取りする。
- **「Wi-Fi接続の有無」と「オンライン/オフライン」を混同しない。** Wi-Fiが無くても4G/5Gが繋がっていれば、それは正常な「オンライン」状態であり、エラー扱いにしてはならない。判定基準は常に「インターネットに到達可能か」であって「Wi-Fiかどうか」ではない。
- **「通信エラー＝即座に画面いっぱいのエラー表示」にしない。** キャッシュがあればまずキャッシュを見せ、裏で最新化を試み、本当にデータが無く取得もできない場合だけエラーを見せる、という優先順位を都度確認する。
- **「Wi-Fiでは動くが5G/4Gでは動かない」問題が見つかった場合は、費用試算より先に必ずそれを最優先で報告・調査する。** これはオシニウムにとって存在意義に関わる致命的な不具合であり、後回しにしてはいけない。
- 出力は必ず日本語、必ず下記の出力フォーマットに従う。

## ステップ0: 前回監査との比較のための履歴読み込み

`.claude/skills/money/history.md`を確認する。ファイルが存在すれば直近のエントリを読み、前回「5G/4Gで動かなかった問題」「高リスクと判定した項目」がその後のコード変更で実際に解消されているか照合する。存在しなければ新規作成し、初回監査であることをレポートに明記する。

## ステップ1: 通信環境そのものへの依存を確認する

オシニウムは、ユーザーが常にWi-Fi環境にいることを前提にしてはならない。以下の環境を想定してコードを検証する（実機での物理的な切り替えテストはこのセッションからは行えないため、コードレベルでの検証と、可能な範囲でのシミュレーター上の疑似確認に読み替える）。

- 自宅Wi-Fi
- 4G / 5G
- Wi-Fiから5Gへの切り替え、5GからWi-Fiへの切り替え
- 通信速度が遅い4G、一時的に不安定な環境、瞬断
- 完全な圏外、機内モード

### 「5Gなのに通信エラー」を最優先で調査する

このセッションで実際に発生した「Wi-FiをOFF→5Gへ切り替え→『グループの読み込みに失敗しました』」という事象を踏まえ、以下をコードレベルで確認する。

- Firebase/Firestoreへの接続を阻害するWi-Fi前提のコードが無いか(`NWPathMonitor`の使い方、`usesInterfaceType`の扱い等、`Managers/NetworkMonitor.swift`を起点に確認)
- Firestoreのリクエストが正常に完了しているか、Firebase Authenticationの状態が通信種別の切り替えで失われていないか
- ネットワーク状態の判定(`NetworkMonitor.isConnected`)が「Wi-Fiかどうか」ではなく「到達可能かどうか」で正しく判定されているか
- Firestoreのオフライン永続キャッシュ(`PersistentCacheSettings`、`AppDelegate.swift`で設定)が実際に効いているか
- 通信種別切り替え時にFirestoreリスナー(`addSnapshotListener`)が切断されたまま放置されていないか、切断後に自動的に再購読される作りになっているか(各ViewModelの`scheduleRetry`系、および`NetworkMonitor.retryWhenOnline`との関係)
- リクエストのタイムアウト設定が短すぎないか
- 通信エラー時にUIが即座にエラー画面へ遷移する設計になっていないか(`GroupViewModel.loadErrorMessage`とその表示先である`Road 画面/AppRootView.swift`の`groupLoadErrorBanner`を起点に、他の同種箇所も洗い出す)
- ネットワーク復帰時に自動的に再取得される作りになっているか

**重要な補足**: 「Wi-Fiが無い＝オフライン」ではない。Wi-Fiなし＋5Gありは正常な「オンライン」である。この前提を壊しているコード（Wi-Fi接続時のみ許可する分岐、Wi-Fi専用のURLSessionポリシー等）が無いか、`allowsCellularAccess`のようなキーワードも含めて横断的に検索する。

## ステップ2: オフラインファースト設計の状況を確認する

完全に通信が無い場合でも、可能な範囲でアプリを使えるべきかという観点から、以下がキャッシュ表示・オフライン利用に対応できているか実装を確認する。

- 既に取得したグループ・タイムライン・予定・カレンダー・ユーザー情報
- キャッシュ済み画像・動画
- 下書き・オフライン中の投稿作成の可否

### 通信復帰時の自動同期

「通信復帰 → Firebaseへの接続確認 → 最新データ取得 → ローカルキャッシュ更新 → 画面更新 → オフライン中に作成したデータの送信」という流れが、ユーザーが手動で「再読み込み」しなくても自動的に行われる作りになっているか確認する。

### ローディングによるカクつき防止

ネットワーク通信中に画面全体をローディング状態にして操作不能にしていないか。理想は「キャッシュ表示→操作可能→裏で通信→到着したら必要な部分だけ更新」という体験であることを確認する。

## ステップ3: 通信量・コストの実装を調査する

推測ではなく、以下を実際にコードから調べる。

### タイムライン
- 1回に取得する投稿数、ページングの有無、`LazyVStack`/`LazyVGrid`の使用状況
- 画像サイズ・サムネイルの有無、動画の自動再生設定、キャッシュ(Nuke等)の設定
- 「タイムラインを開くたびに過去の投稿を全件取得する」ような実装が無いか

### 画像・動画
- アップロード時の圧縮・リサイズ処理の有無(`ImageStorageService.swift`等)、元画像/圧縮後サイズ
- 動画の最大容量・解像度・圧縮率、自動再生の有無
- Storageの実際の使用量が見積もれる根拠(投稿数×平均ファイルサイズ等)

### Firestore/Functions/AI
- リアルタイムリスナー(`addSnapshotListener`)の設置箇所総数と、不要な張りっぱなし(`stopListening`漏れ)が無いか
- 画面を開くたびに全件読み直すクエリが無いか
- AI API(Gemini等)の呼び出し頻度・キャッシュの有無・失敗時のリトライ回数(過剰課金の芽が無いか)
- Cloud Functionsの起動頻度・課金体系

## ステップ4: ユーザー数別の運用費と収益を試算する

最低でも100人・1,000人・5,000人・10,000人・50,000人・100,000人の規模で、Firestore・Storage・ネットワーク転送・AI・Functions・その他APIの月額費用を、ステップ3で調べた実際の利用パターンをもとに試算する。数字の根拠(1ユーザーあたり月間投稿数・閲覧数の仮定など)を必ず明記し、仮定であることを隠さない。

収益側は、現在確定している前提(プレミアムプラン月額400円、無料ユーザー向け動画広告)をもとに、有料会員率・広告eCPM・App Store手数料(30%または15%)を明示した仮定で試算する。

**収益 − (Firestore + Storage + 通信 + AI + Functions + その他)** で利益を算出し、**1ユーザー増加あたりの限界費用**も可能な範囲で示す。

## ステップ5: 危険ラインと改善案

以下のような高リスク要素が実装に存在しないか確認する: 動画の自動再生、大容量動画のアップロード制限の欠如、無制限の画像投稿、大量のFirestore読み取りを招くクエリ、張りっぱなしのリアルタイムリスナー、画面を開くたびの全データ再取得、AI APIの過剰・無制限呼び出し、キャッシュされない画像の繰り返し再取得。

見つかった場合、機能を削れという結論にすぐ飛びつかず、圧縮・キャッシュ・ページング・Lazy Loading・サムネイル・差分同期・リスナー最適化・AI結果のキャッシュ・古いデータのアーカイブ等、コストを抑えつつ機能を維持する改善案を優先して提示する。
