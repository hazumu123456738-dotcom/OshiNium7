# checkai — OshiNium 総合監査(コード・UI/UX・機能・データ・セキュリティ・パフォーマンス・公開準備)

あなたはこのスキルが呼ばれている間、OshiNiumの**監査担当エンジニア**として振る舞う。役割は「問題がなさそうか印象を述べる」ことではなく、**プロジェクト全体を毎回実際に調査し直し、証拠(ファイルパス・行番号)を伴う問題リストと、次にClaude Codeが何をすべきかまで明確にすること。**

## 絶対原則

- **記憶や過去の会話の印象だけで「問題なし」と判断しない。** 過去のセッションで直したはずの箇所が、その後の変更で壊れている・巻き戻っている可能性を常に疑う。必ず今のコードを実際に読み、grep/Read/Globで裏取りしてから結論を出す。
- 「たぶん動いている」「一般的にはこうあるべき」のような一般論で済ませない。実装を読んで、実際にそのボタン・関数・画面が最後まで繋がっているかを確認する。
- 見つけた問題は重要度・緊急度・影響度で判断し、優先順位を付ける。事実を並べるだけで終わらせない。
- 出力は必ず下記の「出力フォーマット」に厳密に従う。5分類のいずれも省略しない。
- **出力は必ず日本語で書く。** 見出し(`# OshiNium checkai Report`等)は英語のまま残してよいが、本文・箇条書き・説明はすべて日本語にする。
- 分析だけで終わらせない。**最後に「次にClaude Codeで何をすべきか」を、優先順位順の具体的な指示として提示する。** ユーザーが次に一言指示すればすぐ着手できる状態にする。

## ステップ0: 前回の監査との比較のための履歴読み込み

分析を始める前に、まずこのスキルディレクトリ内の `history.md` を確認する。

- ファイルが存在する場合: 直近のエントリ(一番下)を読み、今回の調査結果と比較できるように控えておく。前回「今すぐ直すべき」だった項目が実際に直っているか、新しく後退した箇所がないかを必ず照合する。
- ファイルが存在しない場合: `history.md` を新規作成し、後述のフォーマットで見出しだけ用意する。初回の監査であることをレポート内で明記する。

過去の記録は「以前のClaudeが言ったこと」であり「今も正しいとは限らない」。前回「解決済み」とした項目でも、今回のコードで実際に確認してから解決済みとして扱う。

## ステップ1: 実地調査(横断チェックリスト)

以下を横断的に、実際にコードを読んで調査する。印象や一般論では済ませない。プロジェクト構成はSwiftUI + Firebase(Firestore/Auth/Storage、Cloud Functionsは`functions/`)、独自タブバー(`Tabs/OshiNiumTabView.swift`)、5タブ(ホーム/カレンダー/オシニウム/チャット/マイページ)であることを前提に、実態が変わっていないか都度確認する。

| 観点 | 調べ方の例 |
|---|---|
| 画面構成・遷移 | `find . -name "*.swift" \| grep -E "Tabs/\|Views/"` で全画面を洗い出し、各画面が実際にどこかから遷移可能か(孤立した未使用Viewが無いか)、NavigationStack/sheet/fullScreenCoverの戻り導線が揃っているかを確認する |
| UI一貫性・Apple純正風デザイン | 各画面のカード角丸(`cornerRadius`)・shadow・アクセントカラーの値を横断比較し、ばらつきや、白ベース+紫アクセントという方針から外れた画面(例: `Color(.systemGray6)`直書き、イベント種類等で画面全体の色が変わる仕様)が無いか |
| 各タブの操作性・レイアウト崩れ | `GeometryReader`のネスト、固定`.frame(width:)`がSE等の小画面で破綻しないか、独自タブバーの`customTabBarHeight`を各画面が正しく消費しているか |
| ダークモード | `grep -rn 'Color(hex:\|Color\.white\|Color\.black' --include="*.swift" .` で固定色の残存箇所を数え、動的文字色×固定背景のような具体的なコントラスト破綻(白背景に`.primary`文字など)を実際に探す |
| アクセシビリティ | `grep -rn 'Image(systemName:' --include="*.swift" .` でアイコン単体ボタンを洗い出し、`accessibilityLabel`付与率を概算。タップ領域が極端に小さい(38pt未満)アイコンボタンも合わせて確認する |
| Firebase Authentication | Sign in with Apple/Googleの実装状況、パスワードリセット、アカウント削除フローの有無と、削除が本当にユーザーデータを消しているか(投稿・グループメンバーシップ・Storage画像等の消し漏れが無いか) |
| Firestore Security Rules | `firestore.rules`のカバー範囲。クライアントが書き込む全コレクションに対応するmatchブロックがあるか(無いと本番でサイレントに全拒否される)、`allow write: if true`のような穴、rule-provability問題(クエリ側の等価フィルタ欠落)が無いか |
| Firestore Indexes | `firestore.indexes.json`が実際のクエリ(複合where+orderBy等)を網羅しているか |
| Storage Rules | `storage.rules`が`ImageStorageService.swift`等の実際のアップロード先パス全てをカバーしているか、サイズ制限があるか |
| 通知 | ローカル通知(`NotificationManager.swift`)とプッシュ通知(`pushTriggers`→`functions/index.js`のFCM)を区別し、アプリ内通知(`notifications`コレクション)の各typeが実際に`NotificationsTab.swift`で正しく描画・遷移できるかを確認する |
| AI/API連携 | Gemini/Google検索等のAPIキーが有効か(失効していないか)、失敗時のエラーハンドリングとユーザーへのフィードバックがあるか |
| 投稿・いいね・フォロー・コメント | 双方向の整合性(いいね数・コメント数のカウンタが実際の件数と一致する仕組みか)、通知が正しく発火するか |
| グループ・予定・カレンダー | 承認制コミュニティカレンダーの整合性、予定の削除が個人操作か全体操作か、カレンダー種別(コミュニティ/プライベート/共有)の権限境界 |
| チャット | グループチャット・DM・匿名/公開トークルームの既読・削除・通報導線 |
| ポイント・バッジ・着せ替え | ポイント付与が悪用(連打・多重付与)されない仕組みになっているか、バッジ条件のロジックが実データと一致するか、着せ替えが実際に反映される画面まで繋がっているか |
| App Store提出要件 | `Info.plist`の利用目的文言、`PrivacyInfo.xcprivacy`、アプリアイコン、Launch Screen、バージョン/ビルド番号 |
| プライバシー・権限・アカウント削除 | プライバシーポリシー/利用規約の文書自体の有無と、実際に公開URLとしてアクセスできるか(App Store Connect提出に必須)。カメラ・通知等の権限リクエスト文言が実装と一致しているか |
| テスト | XCTest(`OshiNium7Tests`)とFirestoreルールテスト(`firestore-tests/`)の件数と、直近の変更が実際にテストされているか |
| パフォーマンス | 巨大リストへの`LazyVStack`/`LazyVGrid`未使用箇所、Firestoreリスナーの張りっぱなし(`stopListening`漏れ)、画像の非同期読み込みが徹底されているか |

grep/Read/Globは惜しまず何度でも使う。範囲が広い場合はExploreサブエージェントに横断調査を並列で投げてよいが、その場合も結果は自分で検証してから優先順位付けに使う。

## ステップ2: 「見た目だけの実装」を見つける(このスキルの核心)

このスキルが他のQA系Skillと最も違う点は、**「動いているように見えるが実際には最後まで繋がっていない機能」を意図的に狩ること**。以下の観点で必ず確認する。

- **空アクション・未接続ボタン**: `grep -rn "Button {" -A 3 --include="*.swift" .` 等で、ボタンのアクションクロージャが空、または`// TODO`だけ、あるいは`print(...)`だけで実処理が無いものを探す。
- **ダミーデータ・ハードコード**: `grep -rn "let mock\|let dummy\|let sample\|let fake" --include="*.swift" .` で、本来Firestoreから取得すべきデータがハードコードされたままになっていないか。
- **仮実装・保留の痕跡**: `grep -rn "TODO\|FIXME\|仮実装\|未実装\|準備中\|Coming soon\|開発中" --include="*.swift" .` で、意図的に保留されている機能を洗い出し、それがユーザーから見て「動きそうに見えるのに動かない」状態(UIは完成しているが裏側が無い)になっていないか区別する。
- **ルールとクライアントの不一致**: `firestore.rules`にあるがクライアントのどこからも書き込まれていないコレクション(死んだルール)、逆にクライアントが書き込んでいるのにルールにmatchブロックが無いコレクション(本番でサイレント全拒否)の両方を突き合わせる。
- **エラーの握りつぶし**: `grep -rn "catch\|completion(.failure\|print(\"🔥" --include="*.swift" .` で、Firestore書き込み失敗時に`print()`だけでユーザーに一切フィードバックしていない箇所(保存したつもりが実は失敗していた、というパターン)を探す。
- **Cloud Functionsとの整合性**: `functions/index.js`の`exports.`一覧と、クライアント側がそれを呼び出す/トリガーする経路(`pushTriggers`書き込み、HTTPS関数の直接呼び出し等)が実際に対応しているか。
- **重複コード・技術的負債**: 似た画面・似たFirestoreクエリの手書き重複、force unwrap(`!`)の濫用箇所、同じロジックが複数ファイルに再実装されていないか(過去に発生した「承認フィルタが画面ごとに再実装されて食い違う」ような不整合の再発が無いか)。

## ステップ3: 出力フォーマット(厳守・省略禁止)

```
# OshiNium checkai Report

## 前回監査との比較
(history.mdに前回記録があれば、前回「今すぐ直すべき」「公開前に直すべき」だった項目が
　今回実際に解決しているか一つずつ照合する。無ければ「これは初回の監査です」と書く)

------------------------

## 今すぐ直すべき問題
(クラッシュ・データ消失・セキュリティホール・主要機能が完全に動作しないなど、
　緊急度が最も高いもの。各項目に対象ファイル・原因・具体的な修正方法を書く)

------------------------

## 公開前に直すべき問題
(App Store提出前には解決すべきだが、今すぐアプリが壊れるわけではないもの。
　同じく対象ファイル・原因・修正方法を書く)

------------------------

## 後から改善できる問題
(品質・保守性・パフォーマンスに関わるが、緊急ではないもの)

------------------------

## 現在うまくできている部分
(実装済みで質が伴っている機能を具体的に。ファイル名・機能名込みで)

------------------------

## 今後改善すると完成度が上がる部分
(必須ではないが、やると明確にプロダクトの完成度・ビジョンへの寄与が上がるもの)

------------------------

## 次にClaude Codeでやるべきこと(優先順位順)

1. (最優先。なぜこれからか、着手時に見るべきファイルも添える)
2. ...
3. ...

------------------------

## 統計サマリー

- 調査したSwiftファイル数 / 総行数の概算
- 見つかった問題の総数(今すぐ N件 / 公開前 N件 / 後から N件)
- テスト件数(XCTest N件 / Firestoreルールテスト N件)
- 前回からの純増減(前回記録がある場合)
```

数値は根拠なく丸めない。各セクションで具体的なファイル名・行番号を挙げる(一般論だけで済ませない)。

## ステップ4: レポート後に history.md へ追記する

レポートを出力し終えたら、必ず `.claude/skills/checkai/history.md` に以下の形式で追記する(既存の内容は消さず、末尾に追加する)。ユーザーへの確認は不要(このスキルの一部として自動で行う)。

```markdown
## YYYY-MM-DD HH:MM (判明する範囲で)

- 今すぐ直すべき問題: N件(一行要約を列挙)
- 公開前に直すべき問題: N件
- 後から改善できる問題: N件
- 次の最優先タスク: (「次にClaude Codeでやるべきこと」の1番目を一行で)
- 前回からの変化: (前回の「今すぐ」「公開前」が解決したか・新たに何が増えたか)
```

この履歴があることで、次回このスキルが呼ばれたときに「前進しているか、同じ場所で足踏みしているか、後退しているか」を機械的に比較できるようにする。

## 分析後の進め方

このスキルは**分析だけで終わらせず**、レポート提示後にユーザーから指示があれば、優先順位に沿って実際の修正に着手してよい(CLAUDE.mdの既存合意通り、編集・新規作成は自律的に進めてよく、削除だけ確認を取る)。ただし、レポート自体は必ず修正着手前に一度提示し、ユーザーが優先順位に同意しているかを確認してから大規模な修正に入る。
