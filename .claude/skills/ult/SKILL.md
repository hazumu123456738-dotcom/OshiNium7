# /ult — Ultimate OshiNium Audit & Improvement Skill

あなたはこのスキルが呼ばれている間、**技術・セキュリティ・法務・UX・コミュニティ安全・AI・事業・運営の8分野を横断する監査チーム全体**として振る舞う。目的は診断レポートを作ることではなく、**「現在のオシニウムは、この状態でユーザーに公開しても現実的に問題ないのか」を実際のコードから判断できる状態にし、修正できる問題はその場で直しきること**にある。

## 最重要ルール：「現在の実装」を基準に判断する

過去に作った仕様書・過去のセッションでの発言・理想の設計だけを信用しない。必ず現在のプロジェクトを調査する。例えば「オフライン対応済み」と過去の記録にあっても、実際にコードを読んで、本当にキャッシュされているか・5Gで動作するか・通信復帰時に同期するか・Firebaseとの接続が切れた場合どうなるかまで確認する。**仕様書や記憶ではなく、実際のコードと設定を最優先する。**

このスキルは`checkai`(技術的完成度)・`finalcheck`(公開可否の法務/社会的リスク)・`money`(通信耐性/採算性)・`release-analyzer`(リリース進捗評定)と重なる領域を横断的に再統合するものであり、それらのSkillの結論をそのまま鵜呑みにせず、今回もコードを実際に読み直して裏取りする。ただし完全新規に調べ直すより、各Skillの`history.md`を先に読み、「前回時点で何が問題とされ、何が直っているか」を出発点にする方が効率的な場合はそれを起点にしてよい。

## ステップ0：前回監査との比較のための履歴読み込み

`.claude/skills/ult/history.md`を確認する。ファイルが存在すれば直近のエントリを読み、前回のP0/P1課題が今回のコードで実際に解消されているか照合する。存在しなければ新規作成し、初回監査であることをレポートに明記する。

余裕があれば`.claude/skills/checkai/history.md`・`.claude/skills/finalcheck/history.md`・`.claude/skills/money/history.md`・`.claude/skills/release-analyzer/history.md`の直近エントリにも目を通し、他のSkillが既に発見・記録した論点との重複調査を避ける（ただし「解決済み」という記述は鵜呑みにせず、今回のコードで再確認する）。

## ステップ1：プロジェクト全体を把握する

変更を始める前に、以下を対象にプロジェクトを調査する：Xcodeプロジェクト構成、SwiftUI画面構成、Firebase(Firestore/Authentication/Cloud Storage/Cloud Functions)、Push Notifications/APNs、AI API、広告SDK、App Store課金・サブスクリプション、DM、タイムライン、画像投稿、動画投稿、カレンダー、グループ、通知、口コミ、AI機能、キャッシュ、オフライン処理、ネットワーク監視、データモデル、Security Rules、APIキー・秘密情報、外部サービス。現在存在する機能を一覧化する。

## ステップ2：現在のアプリ構成を理解する

以下を明確にする。
- **フロントエンド**: SwiftUI構成、View/ViewModel/Service層、データ管理、状態管理
- **バックエンド**: Firebase、Firestore、Storage、Functions、Authentication、Security Rules
- **外部サービス**: AI、広告、Apple IAP、Push Notification、その他API

それぞれがどのように接続されているかを把握する。

## ステップ3：8分野を監査する

範囲が広いため、Exploreサブエージェントに分野ごとの横断調査を並列で投げてよいが、結論は必ず自分でコードを読んで裏取りしてから優先順位付けに使う。

### ① 技術面

「現在は動いている」だけでなく、ユーザーが増えても安定して動作するかを確認する。確認項目：クラッシュ、メモリ使用量、CPU負荷、バッテリー消費、非同期処理、Main Threadブロック、UIフリーズ、Firebase接続、Firestore読み取り/書き込み、Storage、API、Push通知、エラーハンドリング、タイムアウト、リトライ、データ競合、同時更新、重複処理、pagination、Lazy Loading、キャッシュ。

**通信環境**（特に重要）：Wi-Fi、4G、5G、Wi-Fi→5G切り替え、5G→Wi-Fi切り替え、通信速度が遅い場合、一時的な通信断、完全圏外、機内モードを想定する。オシニウムは「Wi-Fiがない＝オフライン」として扱ってはいけない。4G/5Gが利用可能なら通常通り利用できることを目標とする。

**オフラインファースト**：完全な圏外でも、取得済みグループ・取得済み投稿・カレンダー・予定・ユーザー情報・キャッシュ画像・キャッシュデータなどは可能な範囲で利用できるようにする。通信復帰後は自動同期する。「Wi-Fiでは動くが5Gではグループ読み込みに失敗する」等の問題が存在する場合は最優先で調査する。

### ② セキュリティ面

OWASP Mobile Application Security Verification Standard（MASVS）を参考基準とし、特にAuthentication、Authorization、Secure Storage、Network Security、Privacy、Platform Security、Code Securityを確認する。

**Firebase Security Rules**：「ユーザーAがユーザーBのDMを読み取れる」「他人のプロフィールを勝手に変更できる」「他人の投稿を削除できる」「Storageの他人の画像を自由に操作できる」等がないか確認する。**UIでボタンを隠しているだけでは安全とは判断しない。** Firestore/Storage/Backend側で権限が強制されていることを実際のルールファイルを読んで確認する。

**秘密情報**：API Key、Secret、Token、Password、Private Key、Firebase秘密情報、AI API Keyを検索し、GitHub等に公開されてはいけない秘密情報が無いか確認する。

### ③ 法務・権利面

ここはAIだけで「法律的に100%問題ない」と断定しない。AIによる監査は**リスク発見・論点整理**として扱い、必要に応じて専門家確認が必要な項目を明示する。

確認対象：著作権、肖像権、パブリシティ権、商標、投稿画像・動画、ファンアート、X/Instagram等からの転載、AI生成コンテンツ、プライバシー、個人情報、DM、ユーザー投稿、利用規約、プライバシーポリシー、投稿削除、通報、アカウント削除、サブスクリプション、広告、特定商取引法等の表示。

**UGC**：不適切コンテンツ・通報・ブロック・投稿削除・運営への連絡が実装されているか確認する。AppleのApp Review Guidelinesでは、UGC/ソーシャルネットワークを含むアプリについて、不適切コンテンツへの対策・通報機能・ブロック機能・連絡先等が求められている（可能ならWebFetchで最新のガイドラインを確認し、確認できなかった場合はその旨明記する）。

### ④ UX・ユーザー体験

実装者目線ではなく、**初めてオシニウムを使うユーザーの視点**で確認する。

**初回体験**：インストール→起動→ログイン→推しを選択→グループ参加→ホーム→タイムライン→予定→投稿→DM、まで迷わず進めるか確認する。

**エラー時のUX**：通信エラー、Firebaseエラー、投稿失敗、DM失敗、画像/動画アップロード失敗、AIエラー、通知エラー等で、画面全体が壊れたりユーザーが何もできなくなる設計になっていないか確認する。

### ⑤ 安全・コミュニティ面

SNSとして運営できるかを確認する。対象：誹謗中傷、荒らし、スパム、なりすまし、迷惑DM、不適切画像・動画、個人情報投稿、未成年ユーザーへのリスク、外部誘導、詐欺、推し同士の対立、大量通報、Bot。

**DM**：無料ユーザーのDM送信に月間制限があるか（目安：月100件程度）、プレミアムはDM実質無制限か、ただしBot・スパム・短時間大量送信への安全上のレート制限はプレミアムでも維持されているかを確認する。実際の実装（送信回数のカウント箇所・Firestoreルール）を読んで裏取りする。

### ⑥ データ・AI面

AIが関与する機能をすべて確認する（予定作成AI、投稿補助AI、レコメンド、テキスト生成、AI検索、その他Gemini/OpenAI API等）。

**AIの誤動作**：AIが生成した情報をそのまま重要データとして登録していないか確認する。例えばイベント情報なら「AI→候補生成→ユーザー確認→登録」が基本になっているかを確認する。

**AI安全性**：Prompt Injection、不正入力、個人情報送信、不適切生成、API Key漏洩、AIコスト暴騰、無限APIリクエストを確認する。

### ⑦ 成長・事業面

「ユーザーが増えるか」を確認する。

**ユーザー行動**：新規登録→推し登録→グループ参加→タイムライン閲覧→投稿→他ユーザー発見→DM→再訪問、というループが成立するか分析する。

**指標**：DAU、MAU、継続率、投稿率、DM利用率、グループ参加率、新規登録率、退会率、サブスク転換率等を可能な範囲で確認できる設計になっているか（Analytics導入状況等）を確認する。

### ⑧ 運営・保守面

リリース後に運営できるかを確認する。必要な管理機能：ユーザー検索、アカウント停止、投稿削除、DM対応、通報確認・処理、不正ユーザー確認、AIログ、エラーログ、Firebaseログ、サブスク状態、広告関連、問い合わせ対応。1人運営という前提を踏まえ、現実的に対応できる体制かを評価する。

## ステップ4：問題を優先順位付けする

発見した問題を以下の4段階に分類する。

- **P0（即修正必須）**：他人のDMを見られる、Firebase権限突破、API Key漏洩、アプリが起動できない、決済に重大な問題、等
- **P1（リリース前に修正推奨）**：5Gで主要機能が使えない、投稿が消える、DMが正常に送れない、重大なUX問題、等
- **P2（早期改善）**：一部画面の遅さ、キャッシュ不足、不要な通信、等
- **P3（将来的改善）**：UI細部、追加分析、高度な最適化、等

## ステップ5：修正できる問題は実際に修正する

このスキルは監査レポートで終わらせない。コード上で安全に修正できる問題については、**調査→修正→ビルド→実機確認→再確認**まで実行する（`verify` Skillの手順に従う：TEMP DEBUGでの画面到達→確認後の完全削除→再ビルド→再インストール→起動確認のサイクルを省略しない）。

ただし、以下のような取り返しがつかない操作・重大な操作は勝手に実行せず、**「人間による確認が必要」として明確に報告する**：
- 法律判断が必要な事項
- 外部契約に関わる事項
- Apple Developer設定の変更
- 本番Firebase設定（`firestore.rules`/`storage.rules`）のデプロイ（CLAUDE.mdの既存合意通り、変更後は全文を提示してユーザーに手動デプロイを依頼する）
- Cloud Functionsの新設・デプロイ（新しいバックエンド機能の追加は、本CLAUDE.mdの精神に沿ってユーザーの明示的な許可を得てから着手する）
- 本番データの削除
- 課金設定の変更
- 重大なアーキテクチャ変更

新規Swiftファイルを追加する場合は`project-setup` Skillの手順（`xcodeproj` gemでの`.pbxproj`登録）に従う。ファイルの削除が必要な場合はCLAUDE.mdの既存合意通り必ずユーザーに確認を取る。

## ステップ6：修正後に再監査する

修正したら必ずもう一度検査する。例えば「5Gでグループ取得失敗」を修正した場合、修正して終わりにせず、Wi-Fi/5G/Wi-Fi→5G/5G→Wi-Fi/オフライン/復帰、それぞれの状態を再確認してから完了とする。

## ステップ7：リリース前チェックとしての総合判断

最後に「このアプリをApp Storeに提出できる状態か」を総合判断する。

```

（history.mdに前回記録があれば、前回のP0/P1が今回実際に解消しているか照合する。
　無ければ「これは初回の監査です」と書く）

------------------------

■ 8分野スコア

| 運営・保守 | /100 | 🟢/🟡/🔴 |

（スコアは実際に確認できた項目数・重大度・未確認項目数を根拠として算出する。
　根拠なく丸めない。各スコアの下に、何を根拠にその点数にしたか一言添える）

------------------------

■ 発見した問題
（各問題について：問題／発生場所(ファイル:行)／原因／重大度(P0-P3)／
　ユーザーへの影響／運営への影響、を明記する）

------------------------

■ 実際に修正した問題
（各修正について：修正内容／修正ファイル／修正理由／テスト結果(ビルド・実機確認の結果)
　を明記する）

■ 未修正問題
（なぜ修正していないか／人間の判断が必要か／外部設定が必要か／専門家確認が必要か、
　を明記する）

------------------------

■ リリースブロッカー
（「これを直さないとリリースしない方がいい」という問題を明確に列挙する。
　無ければ「現時点でリリースブロッカーは確認されていない」と明記する）

------------------------
```

不明な項目は推測で「問題なし」と判断せず、**「未確認」**と明記する。問題が無ければ問題なしと報告し、問題があれば隠さず報告する。

## ステップ9：レポート後にhistory.mdへ追記する

レポートを出力し終えたら、必ず`.claude/skills/ult/history.md`に以下の形式で追記する（既存内容は消さず末尾に追加。ユーザーへの確認は不要）。

```markdown
## YYYY-MM-DD HH:MM

- 総合判定: 🟢/🟡/🔴（一言要約）
- 8分野スコア: 技術xx/セキュリティxx/法務xx/UXxx/安全xx/AIxx/事業xx/運営xx
- P0件数: N件（一行要約）
- P1件数: N件（一行要約）
- 今回実際に修正した件数: N件
- リリースブロッカー: （あれば概要、無ければ「無し」）
- 前回からの変化: （前回のP0/P1が解消したか、新たに何が増えたか）
```

## 最終目標

/ultの最終的な目的は、オシニウムを「個人が作ったアプリ」から「実際にユーザーを受け入れて運営できるサービス」へ引き上げることにある。単に機能があるだけでは合格としない。**動く＋安全＋法律・権利上のリスクを把握している＋ユーザーが使いやすい＋コミュニティを安全に維持できる＋AIを安全に利用できる＋ユーザーが増えても成立する＋運営・保守できる**、この8つを満たした状態を「オシニウムとしてリリース可能な状態」と定義し、実際のプロジェクトを調査しながら検証し、可能な問題は自律的に修正し、修正後まで確認して完了させる。
